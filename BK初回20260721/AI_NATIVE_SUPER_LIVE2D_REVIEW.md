# 「AIネイティブなスーパーLive2D」として有効か — 実装前再検討(2026-07-19)

> ユーザー指摘「今のままだと普通のLive2Dとあんまり変わらない気がする」を
> 受けた再検討。前提は変えない: 原画ピクセル維持/Gemini素材生成/
> スマホ+Claude完結/VTuber・可愛さ・3Dゲームの3要件。実装はしていない。

## 1. 指摘は正しい — どこが「普通のLive2D」なのか

現計画([`REAL_ART_LIVE2D_PLAN.md`](./REAL_ART_LIVE2D_PLAN.md))の
ランタイム構造を分解すると:

| 要素 | 普通のLive2D | 現計画 |
|---|---|---|
| レイヤー分解した原画をワープ | ○ | ○(同じ) |
| まばたき・口パクのパーツ差し替え | ○ | ○(同じ) |
| 正面±30°の擬似回転 | ○ | ○(同じ) |
| 中間域のワープ品質 | プロのリガーが手調整、**むしろ向こうが上** | Claudeのコード調整 |

つまり**ランタイムの動作原理だけ見れば、Live2Dの下位互換になりかねない**。
これが指摘の正体であり、正しい。「安く作れるLive2D」は価値だが
「スーパー」ではない。

## 2. 何が「スーパー」を生むか — 重心の反転

Live2Dの構造的本質は「**キーフレーム(実絵)が極端に少ないので、
ワープが主役**」であること。だから大角度で破綻し、真横・背面は原理的に
出せず、新表情・新衣装のたびにリガーの手作業が要る。

AIネイティブ方式の本質はその逆で、**「実絵のキーフレームを生成で
無限に増やせるので、ワープは補間糊に格下げする」**こと:

```
Live2D     : 少数の絵 + 強力なワープ(主役) → 中間は綺麗、範囲外は破綻
AIネイティブ: 多数の実絵キーフレーム(主役) + 弱いワープ(糊)
             → どの状態も「本物の絵」、ワープは隣接キーフレーム間の数°〜
               数十%だけ埋める
```

この反転が設計に入っていれば「スーパー」と呼べる。入っていなければ
普通のLive2Dである。判定基準はランタイムではなく**キーフレーム密度と
その供給パイプライン**にある。

## 3. 「スーパー」の具体的な差別化点(前提の範囲内)

1. **全周実絵回転**: 4面ではなく**8〜12方向のビューリング**をGeminiで
   生成し、隣接ビュー間だけをワープ+クロスフェードで繋ぐ。1区間あたり
   30〜45°の補間で済むため破綻域が消え、Live2Dが原理的にできない
   **真横・背面込みの360°を「常に本物の絵」で回せる**。3Dゲームの
   ビルボードスプライト要件とも資産が完全共用になる。
2. **状態格子(ビュー×表情×口形状)のオンデマンド拡張**: 必要になった
   キーフレームだけ後からGeminiで追加生成し、格子に挿すだけで機能が
   増える。Live2Dの「新表情=リグ改修」に対し、こちらは**「新表情=
   画像1枚+マニフェスト1行」**。運用中に育つアセットという点が
   AIネイティブ。
3. **リグをコード/JSONマニフェストとして持つ**: 切り出し領域・
   アンカー・スパイン定義を宣言データ化する。(a)自然言語フィードバック
   →Claudeが決定的に修正(生成ガチャなし)、(b)衣装替え・別キャラでも
   Geminiに同ポーズで出させれば**同じリグがそのまま再適用**できる。
   Live2Dのリグはモデルごとの手作業一点物で、これができない。
4. **自己QCループ**: ヘッドレスChromiumでClaudeが全ビュー×全表情を
   自動撮影・目視検査・修正。Live2D制作における「リガーの目」を
   閉ループで代替する。制作工程に人間の専門技能とGUIツールが不要に
   なること自体が最大のコスト差別化。

## 4. それでもLive2Dに勝てない点(正直な記述)

- **中間域のワープの滑らかさ**: プロが手調整したLive2Dの±30°は
  本方式の糊ワープより滑らか。対抗はキーフレーム密度を上げて
  ワープ距離自体を短くすること(勝ち方が違う)。
- **キーフレーム間の画風一貫性はGeminiの生成品質に依存**:
  ビュー間で服のディテールが揺れるリスク。防衛はQCループでの検出+
  再生成、および目・口など**差分領域だけ合成**して他を原画で固定する
  運用(計画書§3の防衛線)。
- **物理(髪揺れ)の質**: Live2D の物理エディタ相当は自前実装
  (PoCのばねスパインを流用)。当面は簡素で良い。

## 5. 結論と計画への反映

**有効。ただし条件付き** — 「4面+±30°ワープ」で止まると普通の
Live2Dの廉価版に堕ちる。スーパーであるための設計コミットメントとして
以下を計画に組み込む(実装順序は変えない、§6試作の次段以降で効く):

1. 角度は**ビューリング8方向以上**を正式目標とする(4面は初期セットに
   格下げ)。
2. ワープは**隣接キーフレーム間の補間糊**と位置づけ、単独で大角度を
   支えさせない。
3. アセットは**状態格子+JSONマニフェスト**で管理し、オンデマンド
   拡張を前提に置く。
4. 制作は**Claude自己QCループ**で回し、人間はスマホからの自然言語
   フィードバックのみ。

この4点が入っている限り、本方式は「Live2Dを安く真似たもの」ではなく
「実絵キーフレームを生成で無限供給できる前提で設計し直したLive2D」に
なる。それがAIネイティブの意味である。
